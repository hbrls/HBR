# 依赖库（Dependency Inventory）

> updated_by: HBR - GLM-5
> updated_at: 2026-07-02 19:30:00

## 审查目标

- 定位项目全部「依赖声明文件」，枚举所有「显式依赖 / 第一层依赖」（直接由项目声明的坐标、包、模块、本地二进制），不展开依赖库自身传递引入的二级及以下依赖。
- 对每一个第一层依赖逐个分析其功能、作用、潜在优势与潜在劣势，形成可审计的依赖清单与质量画像。
- 识别依赖治理层面的系统性风险：版本管理双轨、能力重叠、僵尸/废弃依赖、安全漏洞、供应链可信度、合规与隐私采集、供应商锁定。
- 为后续 Phase（Build、基础框架、Utils、SDK 等）提供统一的依赖事实底座，避免各维度重复枚举、口径不一。

## 核心关注点

- **依赖声明文件定位**：是否识别出全部依赖声明入口（如 Web 的 `package.json` / lockfile / monorepo workspace 配置，Android 的 Gradle Version Catalog / 各模块 `build.gradle` / 根构建脚本 classpath，iOS 的 `Podfile` / `Package.swift` / `*.xcconfig`，以及本地 `libs/`、`vendor/`、`node_modules` link 等本地二进制入口）；是否存在「声明层面不可见」的通配引入（如 `fileTree`、`link:`、`path:`、git submodule）。

- **第一层依赖枚举完整性**：是否覆盖运行时依赖、开发依赖、构建插件/编译期处理器、测试依赖、本地 AAR/JAR/framework/动态库等全部分类；是否区分「活跃引入」与「已注释/未启用」的依赖；是否记录每个依赖的坐标、版本、引入位置与引入方式（`implementation`/`api`/`dependencies`/`devDependencies`/`classpath` 等）。

- **逐依赖功能与作用分析**：是否对每个依赖说明其在项目中的功能定位与承担的职责；是否明确其归属的技术分层（构建、基础框架、Utils、业务、SDK、测试、可观测等）。

- **潜在优势评估**：是否分析该依赖带来的工程价值（如减少样板代码、统一能力、性能/兼容性收益、生态成熟度、与项目范式的契合度）。

- **潜在劣势与风险评估**：是否识别该依赖的代价与风险，包括但不限于：版本过旧/已废弃/已 EOL、与项目其他依赖主版本不一致、与项目自有实现或同类型库能力重叠、包体积/性能/启动耗时影响、闭源不透明、供应商锁定、历史安全漏洞（CVE）、私有 API 依赖、合规与隐私采集面。

- **版本治理一致性**：是否使用统一的版本管理入口（lockfile / 版本目录 / 锁定文件）；是否存在硬编码版本游离于统一入口之外；版本号是否语义化、可解析（避免 tag 形式、范围符 `+`/`^` 滥用导致不可复现）；主依赖与配套子库（agent/plugin/converter/integration 等）版本是否同源同步。

- **能力重叠与去重**：是否存在多套同职责库并存（如多 JSON 库、多异步范式、多路由/多定位/多日志/多缓存体系、双 converter 注册等）；是否明确单一职责实现与迁移收敛方向。

- **僵尸与遗留依赖**：是否存在已无实际作用（如被新系统/新 minSdk 取代）、仅注释残留、坐标属已废弃体系（如旧 support 库、Fabric/GCM 等）的依赖；是否具备清理路径。

- **安全与合规**：依赖是否来自可信仓库与可追溯来源；是否存在已知 CVE 或被弃用的安全敏感库；闭源/风控/生物特征/设备指纹类 SDK 的采集面是否满足隐私合规（GDPR/区域隐私法）；本地二进制是否可追溯版本与来源。

- **供应链与可观测性**：是否具备依赖准入与生命周期管理（创建-使用-废弃-清理）流程；是否定期执行依赖安全扫描与升级评估；是否维护全量依赖清单文档。
